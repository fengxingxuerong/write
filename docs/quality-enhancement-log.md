## 九、2026-09-12（晚）第 11 角色「大纲终审官」写前守门（结构打回权前置版）

### 背景

终审官《断脉逆命诀》二审暴露的能力边界：其打回重写权仅限单章层级，二审抓出的三个结构级问题

修章治标不治本。与其等收官才发现（已烧完全书配额），不如在写第 1 章之前就守门——
大纲是全书唯一的低频高价值产物，守门成本一次性、收益全书级。

### 新角色：大纲终审官（OUTLINE_REVIEWER）

- **挂载点**：Phase 1.5——规划官出大纲 + concretize_world 之后、第 1 章动笔之前；`--no-outline-review` 可跳过（默认开启）
- **链路**：`OUTLINE_REVIEWER_CHAIN`＝商汤 deepseek-v4-pro K2 主 → glm-5.2 K1 备（max_tokens 8000：pro 思考链 2000-2900 + 修订版大纲全量 JSON）
- **检查清单**（由真实成书教训沉淀成硬规则）：①伏笔分布——单章新埋 ≤2 条、第 1 章限 1-2 条核心伏笔、总数 ≤ 章节数×0.8、每条须有回收安排；②末章必须有结局——禁"前夕态"收尾；③单章信息密度——新设定 ≤2 个/章；④钩子链——每章有钩子且类型不连续重复；⑤主线闭环——动机-目标-障碍-代价 + 金手指带代价；⑥节奏——连续 2 章纯铺垫算塌陷
- **输出**：JSON（pass/overall/issues 带大纲证据/advice/revised_outline）；pass=false 时修订版全量大纲必填
- **守门逻辑**：pass 放行；fail 且修订版有效 → 顶层字段兜底合并（title/blurb/tags/protagonist/world/hook 从原大纲补齐）→ 再过一次 concretize_world（幂等）→ 采纳修订版；修订版缺失/无效则放行原大纲（问题清单留痕）
- **LLM 全挂/解析失败**：放行原大纲不阻塞生成（守门岗不得挡住整本书，与项目兜底原则一致）

### 新角色：读者官（READER_PROXY）

- **链路**：商汤 dsf-flash K3（与状态提取官同 key 分摊轻任务），max_tokens 500，每章 1 次

## 十八、2026-09-26 门禁 v7 第 13 项根因修复：世界观专名清单注入写手与定点修

### 根因（都在提示词侧，不在模型能力）

把「评审 → 定点修 → 再评审」整条链路拉直后，失败是**必然**而非偶然：

1. **修复侧（决定性）**：`fanqie_review.fix_prompt(review, content)` 只把评审结论抄成一行「- 一致性：大纲世界观专名 12 个在正文一个都没出现…」，**提示词里一个专名都没有**。定点修模型收到的指令是「把世界观写进正文」却不知道本书世界观叫什么——修不动是意料之中，v7「定点修一轮后仍残留」由此解释。
2. **生成侧**：`scene_prompt` 注入的是整段 `world` JSON（「本书世界观（必须沿用）」），而评审用的是 `extract_world_terms` 切出的**专名**、按**字面命中**计数。写手自由转述设定 ⇒ 0 命中 ⇒ 直接记「世界观未落地」（重写级阻断项）。

## 二十、2026-09-26 门禁 v7 第 16 项治理：编造命中从「只记录」变「即处置」

### 证据链（先确认问题在哪一层）

### 改动（修复侧回灌 + 生成侧预防）

- **`fact_fix_prompt`（新）**：只处置命中的断言，每处三选一——①删；②改写成非断言（「据说…」「他也不确定…」），确保后续章节不把它当既定事实；③确为剧情必需时在本章内补出来龙去脉（谁、何时、为何、在哪），让它成为本章首次确立的设定。其余段落一字不改，字数下限沿用 `FIX_MIN_RATIO`（**禁止以删代修**）。
- **`fact_check_stage`（新）**：`核查 → 命中即定点修 → 复检`，两条铁律：
  1. **只有复检命中数下降才采纳，否则回滚**，保留原文与首轮命中——「换了段文字」绝不等于「问题解决了」（与评审修同一验收哲学）；
  2. **台账口径始终是前章**：复检用的是修复前就存在的户籍表/数字台账/跨章状态，**绝不回灌自证**——先把编造写进台账再复检等于把检查废掉，这条绝不能开。
  - 成本：0 命中章零额外开销；命中章多 2 次调用（修复 + 复检）。
- **写手预防**：`scene_prompt` 加【事实与数字硬约束】——数字只准取自台账、台账没有的一律不许凭空写；背景细节（债务/年份/地点/师门/旧约/存放处）首次出现必须在本章交代来龙去脉，禁止以「既定事实」口吻引用。
- 两处调用点（主循环 7.60、结构补章）改走 `fact_check_stage`，`fact_check` 记录格式不变（`idx/fabrications/error` + 新增 `repaired`），门禁第 16 项读取逻辑**零改动**。

## 二十五、2026-09-28 文风指纹 P1-1 收口：共享装载 + 评审证据 + 编辑保文风 + 双入口 + 真机单发验证

4. **指纹块优先级条款**：注入前检查发现参考文对白 6% 与准则 25%~45% 直接冲突——描述性数字会诱导模型少写对白，`style_fingerprint_block` 块头加「与准则冲突时以准则为准」，防「学分布」变「学低对白」

1. **`scene_planning_prompt` 把 goal 限死「20字内」**：模型倾向写「局势逆转，危机爆发」这类不含爽点词的文案，规划层「至少安排 1 个外显爽点场景」的要求**落不到 goal 文本上**
2. **兜底骨架一个爽点场景都没有**：`fallback_scenes` 的四个 goal 全是固定文案（场景铺垫/事件推进/局势逆转/收束钩子），关键词通道对兜底章**必然不命中**——而规划链失败正是限流期的常态

## 二十九、2026-09-29 桌面端补齐「修复」闭环——把断供历史送进无状态引擎

第二十五节留的遗留：「桌面端**修复**闭环缺跨章上下文（`MultiPassChapterEngine` 是无状态单章引擎，拿不到前序章 💥 序列）」。本节补齐，**不依赖任何 LLM 配额**（纯工程）。

### 问题

桌面端多章连写的循环在 `GenerateViewModel`（`for (int i = 0; i < count; i++)`），但引擎 `MultiPassChapterEngine.generate()` 只拿到 `ContextBundle` 里的**当前章**信息。断供是**跨章**形态（连续 N 章无外显兑现），引擎无从判定 —— 于是桌面端虽有 Python 同款的检测器（`PipelineQa.payoffDroughtZones`，第二十六节补的），却既不能预防升级也不能修复。

### 改动七：历史进 `ContextBundle`，补齐四件套

1. **`ChapterPayoff`（`pipeline_qa.dart`）**：一章的 `thrillPerK` + `sidePerK`，纯数据可跨 Isolate；`of(content)` 现算、`toJson/fromJson` 容错（坏数据不崩整轮生成）。
   > 放在 `pipeline_qa.dart` 而非 `generation_engine.dart` 是为**保持依赖单向**：`generation_engine.dart` → `pipeline_qa.dart`，不反向依赖（否则形成 import 环）。
2. **`ContextBundle.payoffHistory`**：`copyWith` 支持透传；默认空列表 = 无历史 = **不判定跨章断供，行为与旧版完全一致**。
3. **ViewModel 累积**：每章生成后 `_appendPayoff(finalContent)`，滚动保留最近 **8** 章（断供只看末尾连续长度，更早历史不影响结论，留着只是白白跨 Isolate 传数据）；每次任务开始 `_payoffHistory.clear()`。
4. **`MultiPassChapterEngine` 补修**：场景拼装后整章一次性判定 → `needsPayoffRepair`（单章双低 **或** 断供带）→ 触发整章情绪强化 → `acceptPayoffRepair` 验收（字数区间 + 角色名完整 + **必须真补上外显兑现**）。**失败/空产出/未过验收一律返回 null 保留原文**，不阻塞生成。进度回报新增「外显爽点补修（跨章断供 N 章）…」阶段，用户可见。

### 改动九：Dart 侧指纹四件套（与 Python 同口径同键名）

全部落在 `PipelineQa`（与既有度量同处，避免第二套标准）：

### 顺带挖出：双端 `countWords` 是三套不同定义（既有缺陷，本轮只记录不修）

对账时发现 `words` 一项对不上（Python 106660 vs Dart 106636，差 24），逐层定位到根因——**同一个「字数」概念在仓库里有三套实现**：

| 实现 | CJK 范围 | ASCII 字母 | ASCII 数字 |
|---|---|---|---|
| `AppConstants.countWords`（Dart） | 基本区+**扩展A**+兼容区 | 与数字**共用**一个连续标志 → `MVP2024` = **1** | 同左 |
| `generate_novel.count_words`（Python 生成侧） | 基本区+兼容区（**缺扩展A**） | 独立分支 | **独立分支** → `MVP2024` = **2** |
| `fanqie_review.count_words`（Python 质检侧） | **仅基本区** | 不计 | 不计 |

三处都自称「同口径」（`generate_novel.count_words` 的注释直接写「复用 Dart countWords 逻辑」），实际都不同。本书正好有 24 处字母→数字相邻（如 `MVP` 旁跟数字），差值精确等于 24，可完全解释。

**本轮为何不修**：`countWords` 是**全书字数显示与几乎所有密度指标的分母**，改它会连带改动字数显示、达标率、导出统计等一批既有行为，属于产品级口径决定，不该在一个「补指纹内核」的提交里静默变更。故：**只记录 + 在对账测试里显式排除 `words` 并注明原因**，避免后人误以为已对齐。

**影响面评估（供决策）**：九项指纹全是**比率**，分母以 CJK 主体为主，24/106660 ≈ 0.02% 的差异不足以改变任何一项判定（实测九项 diff 全为 0.0000）——所以**本轮功能不受影响**，但字数显示与 `docs/交付文档.md` 里任何「N 字」的表述在两端可能对不上。
