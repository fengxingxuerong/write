# 墨匠 InkSmith：20 万字级小说真实保存压测报告

> 实测日期：2026-09-20 22:54（Dart 3.12.2 / Flutter 3.44.9）
> 复现：`flutter test tool/save_stress_test.dart --reporter expanded`
> 原始数据：`verify-logs/save_stress_raw.txt`

## 结论（先行）

20 万字级全书，经生产同路径 `NovelRepository.saveNovel()`（per-novel 锁 + 原子写 + **写前 rename 零拷贝备份** + index 刷新）真实落盘：

- **保存耗时：中位 10 ms**（10 轮 9–14 ms），用户完全无感；
- **读回耗时：中位 9 ms**（10 轮 8–19 ms）；
- **单次保存写盘 0.7198 MiB**（主文件 737 KiB + index 160 B；`.bak` 由 rename 生成，**零字节拷贝**，不再计入写盘量）——较改造前（1.4395 MiB）**写放大减半**；
- **读回完整性 PASS**：100 章逐章一致、角色/世界观/存稿一致、index 摘要正确；
- **备份语义 PASS**：`.bak` 是「写前上一版」的回滚点（rename 把旧主文件直接改名而来，内容为上一版，与最新主文件不同）——由同一文件落两次不同版本验证。

**结论**：存储写放大改造（写后 copy 最新版镜像 → 写前 rename 上一版回滚点）已生效，写盘量减半，可靠性语义（损坏自愈）不变，延迟无退化。

## 存储写放大改造（2026-09-20）

**改造前**：`writeNovel` = tmp 写 → rename 为主文件 → **copy 主文件为 `.bak`**。每次保存主文件 + 备份全量双写，且 `.bak` 是「写后最新版镜像」。

**改造后**：旧主文件先 `rename` 为 `.bak`（同卷元数据操作、零字节拷贝），tmp 再 rename 为主文件；首写（主文件不存在）时 rename tmp→main 后 copy 一次建初始快照。

- 语义变化：备份从「写后最新版镜像」变为「写前上一版回滚点」；崩溃窗口更窄（连续两次原子 rename）。
- 可靠性不变：任意时刻至少一份完好数据在盘；主文件损坏/缺失时仍可从 `.bak` 自愈。
- 写盘量：每次保存正文只落一次（tmp→main）+ index，`.bak` 零拷贝。

## 压测对象与方法

**真实链路**（非模拟）：`NovelRepository.saveNovel(novel)` → `AppDatabase.withNovelLock` → `writeNovel`（`encodeNovel` JSON 序列化 → tmp 文件写入 + flush → 写前 rename 旧主文件为 `.bak` → rename tmp 为主文件 → `refreshIndexEntry`（index.json 重写）。读回走 `readNovel`（主文件解析，超 10 万字符阈值时 JSON 编解码下沉 compute isolate）。

**20 万字造数口径**：100 章 × 约 2000 字，用项目同款 `AppConstants.countWords` 校验，全书 **200,675 字**（content UTF-16 240,350 字符），另含角色 6、世界观 4、存稿 2，内容为程序生成的散文片段（含对话/标点/换行，JSON 转义占比与真实行文同一量级）。

**测量轮次**：warmup 1 次 → `encodeNovel` ×5 → `saveNovel` ×10 → 文件体积与 tmp 残留检查 → 备份语义验证（同一书 id 落两个不同版本，断言 `.bak` 为版本一/主文件为版本二）→ `readNovel` ×10 → 读回逐字段完整性校验。

## 分项分析

1. **保存耗时构成**：完整保存 10 ms 中，JSON 序列化仅约 2 ms（isolate 分流），其余约 8 ms 为 tmp 写入（737 KiB）+ 两次 rename。改造后不再有 copy 双写，I/O 耗时与改造前基本持平（rename 与 copy 都是写入一版内容 + 目录项更新）。
2. **写放大**：每次保存 = 正文只写一遍（tmp→main）+ index 重写；`.bak` 零拷贝。按最极端场景推算（写作中每 3 秒触发一次自动保存）：约 0.84 GiB/h 写盘，较改造前（1.69 GiB/h）减半。对主流 NVMe（TBW 数百 TB）寿命影响可忽略。*(推算，非实测)*
3. **备份可靠性**：写前 rename 把「上一版」完整保留为回滚点——若新写入内容损坏或写入中途崩溃，旧版仍在 `.bak`，`readNovel` 自愈路径不依赖 `.bak` 是否等于最新版；崩溃窗口从「tmp 写 + rename」+「copy 备份」两段缩窄为两段 rename，任一瞬间磁盘上都至少有一份完好数据。
4. **读回**：9 ms 中位，冷启动打开项目同样无感；大书解析已按设计下沉 isolate，不阻塞 UI。
5. **完整性**：多轮断言全 PASS——原子替换无 tmp 残留、`.bak` 为合法 JSON 且是上一版（版本一）、读回逐章/角色/世界观/存稿一致、index 摘要（字数/章数）正确。

## 风险判断

- **当前（20 万级）无性能瓶颈**，写放大已由设计层减半；真正的增长项仍是**每次保存的写盘量随书体积线性上涨**（但只涨一份正文，不再 ×2）。
- 量级预判（线性外推，未实测）：100 万字 ≈ 主文件 3.7 MiB，单次保存写盘约 3.7 MiB（较改造前 7.5 MiB），`saveNovel` 约 40–60 ms——仍在无感区间尾部。
- 若后续要再降写放大，可行方向（供参考，未实施）：主文件全量 + 章节级增量快照、按时间点/退出才保留多版本备份。当前 20 万级不需要。

## 局限说明

- 单机实测（笔记本 i7-12700H，磁盘介质未探测）；不同磁盘（尤其老式 HDD）延迟量级会不同。
- `flutter test` VM 环境非 Release AOT，绝对数字会略优于本报告，但相对关系（写放大、IO 占比）一致。
- 测试正文为程序生成散文，与真实行文的 JSON 转义占比同量级，但非真实用户文本。
- 备份语义用「同一书落两个版本」做确定性验证（rename 与 copy 的产物在该场景下可区分：rename 备份=版本一，copy 备份=版本二）。文件系统 mtime 粒度不足以稳定区分 rename/copy，故未用时间戳判据。
