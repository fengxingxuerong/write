# 2026-10-20 桌面端《远航星》"质量很差"事故：离线占位草稿 + 章首断层 + 检查器误报

## 一、用户报告

> "这个项目我用桌面端写小说发现质量很差，里面的第一句话就感觉是断层，就是不像一个小说第一章的开头。"

症状具体到「**第一句**」——不是笼统的"文笔差"，而是第一句就读不通。

## 二、根因①：那本书根本不是 LLM 写的，是内置「离线模板引擎」拼的

证据链（用户机器上 `%APPDATA%/InkSmith/墨匠/novels/` 里的《远航星》，3 章，2026-10-18 22:42）：

| 书里的句子 | 实际来源 |
|---|---|
| `话音未落，` `靴声由远及近，` `消息比人先到——` `说来也巧，` `第二遍钟响时，` `人还没坐稳，` `门帘一掀，` `一切要从那件事说起：` | `lib/engine/template_engine.dart` 的段落引导语池（27 条） |
| `齐灵在心里飞快地权衡：退，前功尽弃；进，十死无生。`（第 1 章）<br>`陆长风在心里飞快地权衡：退，前功尽弃；进，十死无生。`（第 2 章） | `lib/engine/corpus/beat_corpus.dart` 同一条模板 `{name}在心里飞快地权衡：…`，只换了名字 |
| 大段 `「这世上的便宜没有白占的…」「他们都以为你死在那一年…」` | `template_engine.dart` 的 `_dialogues` 对白池 |
| `古剑 / 玉佩 / 令牌 / 秘境图 / 铜镜 / 骨笛` | 同文件 `_objects` 物件池 |

引擎选择处（`lib/core/di/providers.dart`）：`llmSettingsProvider.useLlm` **默认 false** → 直接 `TemplateEngine()`；
只有 `useLlm == true && config.isConfigured` 才走 `LlmEngine`。
而应用数据目录下**没有 `llm_settings.json`**（只有一份 7 月遗留备份，内容是 `provider=ollama @ localhost:11434`）。

**结论：桌面端当时没有连上任何模型，是纯离线"占位草稿"在出字。** 这个引擎是设计上的占位实现（零网络、可复现的语料拼句），
从来不是"能投稿的正文"——但 UI 上只有一行灰字「🧩 模板生成（零网络离线）」，用户会把它当成 AI 产出。

## 三、根因②：为什么"第一句"就是断层

章首避雷逻辑（`_weaveBeat`）**只防了"以天气起手"**（`_weatherOpenRe` 查雨雪霜雾风），
**没有禁止"需要前指语境的连接词"**。于是全书第一句可以抽到：

> **话音未落**，齐灵把秘境图用布裹好，贴身收妥。

「话音未落」必须挂在上一句台词上，可这是全书第一句——前面什么都没说过。同类还有
`第二遍钟响时，`（没有第一遍）、`消息比人先到——`、`到了这个地步，`、`人还没坐稳，`、`看热闹的人还没散，`
`一切要从那件事说起：`——全是"承接前文"的句式被放在章首。

## 五、顺带修掉的检查器误报（不是预期问题，是检查器造谣）

改完生成侧后 `test/engine/quality/writing_ability_test.dart`（产品能力下限门禁）变红，
按"先双向归因"逐条查过——**两处都是检查器误报**，不是内容退化：

### 5.1 剧情矛盾误报（死者复活）
`_extractDeadCharacters` 取死亡词前 15 字做滑窗，把「被**退婚**羞辱，濒死」「说**明水**越」
这类**碎片**当成了死者名字；而同一碎片又在后一章出现（「退婚的帖子当着满堂人的面」），
于是把一本正文毫无问题的书报成「剧情矛盾 5 处」。

修法：新增 `_looksLikeName()`（首字须为姓氏，或前一字是「小/老」），与 Python
`scripts/fanqie_metrics.py::looks_like_name`（"首字是姓才算人名"）**同口径**——Python 侧是主流水线，以它为准。
同时把 Dart 的 `_surnames` 从 86 个补齐到 Python 全表（原表**漏了「陆/林/宋/程」**，正文实测主角「陆沉」「林舟」就在其中，漏姓会整条漏掉真人物的死亡矛盾）。

### 5.2 人名笔误误报
`_extractPersonNames` 的文档注释一直写着"按**姓氏 + 1~3 字**列出候选"，**实现里却从来没有这道闸**。
于是「我不说」「也不看」「在琉璃京看着」被切成 `我不 / 也不 / 在琉 / 在琉璃`——只因后一个字是动词（后缀线索）就进了候选，
两两编辑距离＝1 → 把干净的书报成「人名不一致 3 处」。修法：第一遍频次统计里补上同一道 `_looksLikeName` 闸。

> 哲学与本文件既有的 `_isNonNameTail` 一致：**宁可漏报，也不误报污染结论**。

## 七、顺带修掉的第二处配置欠账：规划官输出预算 4096 太小

追查真机链路失败时暴露的第二个缺陷，与本轮主题同源（都是"桌面端看起来能用、实际跑不通"）：

`FixedWorkflowPreset` 里所有角色共用 `endpoint()` 的 `maxTokens: 4096`。
而规划官要产出**多章大纲 JSON**，且当前规划链上的模型都会先花一大笔额度思考——
直连实测 `glm-5.2` 规划 3 章大纲时 `reasoning_tokens` 在 1338~4436 之间剧烈波动：

| 实测 | max_tokens | reasoning_tokens | 结果 |
|---|---|---|---|
| glm-5.2（K1） | 4096 | 1338 | 恰好挤进，JSON 被压成不缩进的单行 |
| glm-5.2（K1） | 12000 | 4436 | 完整带缩进 JSON，`finish_reason=stop` |
| 流水线实跑 | 4096 | — | **JSON 截断在 `"origin"` 字段中间** → 解析失败 → 整轮规划失败 |

也就是说 4096 是**赌运气的边界值**：思考多花一点，正文就被截断。
修法：`planner` 单列 `maxTokens: 12000`（审校同链一并继承），对齐 Python 侧规划官
2026-09-30 因同类事故定下的 12000。并在 `fixed_workflow_preset_test.dart` 钉住
`>= 12000`，防回退。

## 八、真机链路的结论与遗留

本轮真机验证（`NOVEL_LIVE=1`，目标 9000 字 / 3 章）**未跑通**，如实记录：

| 尝试 | 观察 |
|---|---|
| 第 1 次 | AMD 规划超时（>90s）；备用 glm-5.2 返回半截 JSON → 规划失败 |
| 第 2 次 | AMD 网关 **504「AI 服务负载过高」**；glm-5.2 返回为空 → 规划失败 |
| 第 3 次（预算已提到 12000） | 同第 2 次：AMD 504 → glm-5.2 返回为空 → 规划失败 |

直连端点层面两者都是好的（AMD 一次 20.8s 出完整规划 JSON；glm-5.2 一次 75.9s 出完整
4 章大纲、`finish_reason=stop`）。流水线连续三次失败集中在两点：

1. **AMD 今天在高负载**：直接回 504（不是限流 429，是网关过载），这是外部状态；
2. **glm-5.2 作规划官备用不可靠**：直连成功那次的 `reasoning_tokens` 已到 4436；
   换成流水线里更长的规划 prompt 后，思考链很可能吃满 12000 预算 → 正文 0 字 →
   "返回为空"。这与项目既有结论一致（`glm-5.2` 长 prompt 下思考吃满 token、恒空正文，
   见 `memory: novel-writer-project` 与 `docs/交付文档.md`）。

**术语**：这是外部端点负载 + glm 长 prompt 思考死循环问题，不是本轮代码改动引入的；
但本轮把它的**可观测性**补上了——失败信息现在写明端点名、响应长度、头与尾，
"截断"与"空响应"与"报错对象"一眼可分（此前只有一句「大纲规划失败：{」）。

遗留（需用户定夺）：
- `role_workflow_live_test.dart` 的路由超时是上一轮为"快速切链"设的，当时规划主力不是
  AMD；现在规划主力是 AMD、备用 glm-5.2 单次就要 76s，这个值需要重估（改它属于测试调参，
  不在本轮范围，故未动）。产品默认的 3 分钟明显更宽容——AMD 健康时 20.8s 就能出规划。
- 规划链的**备用位**仍是 glm-5.2（长 prompt 思考吃满、返回空正文）。备位换成商汤
  `deepseek-v4-flash` 的方案已拟好但**未实施**：属角色分配调整，需真机复测后再定。

## 九、续：首次启动自动接入本机 AI（用户决定："有 Key 就自动开启"）

一节的事故形态是"用户以为在用 AI，其实在跑占位草稿"。第八节把可观测性补齐了，
本节解决**触发**：默认值不改，但**首次启动时若本机有密钥就自动接上**。

| 位置 | 改动 |
|---|---|
| `lib/models/llm_config.dart` | `LlmSettingsRepository.hasPersistedFlags()`：区分「用户明确关掉了 AI」与「用户从没做过选择」——后者才是可以自动接管的时机 |
| `lib/core/di/providers.dart` | `autoEnableLlmFromLocalKeys(repo, {loadLocalKeys})`：三条触发条件全满足才写——① 从未持久化过引擎开关；② 本机 `.env.local` 能解析出密钥；③ 按固定分工装配后**写手主位**（AMD `DeepSeek-V4-Flash`）可用。全程失败静默，绝不阻塞启动 |
| `lib/main.dart` | `AppDatabase.init()` 之后、`runApp` 之前调用一次 |
| `lib/ai_pipeline/services/env_keys_loader.dart` | 复用既有的「从本机 .env.local 自动发现密钥」（该文件原为并行会话在飞工作，本轮经用户同意一并入库） |

**为什么判据是「从未持久化过开关」而不是「useLlm == false」**：后者会让
「用户关掉 AI → 下次启动又被自动打开」，开关等于失效。一旦用户显式开/关过一次，
这里就再也不插手。

**为什么单模型取写手主位**：一键生成是「一个模型干全部活」（正文/标题/摘要/润色），
写手位是四个角色里最贴题的那个；且它与 AI 流水线页的固定分工共用同一套端点表，
两边口径不会漂。

## 十、规划官模型选型的实测裁决：`deepseek-v4.1-flash` 换不上去

用户提议把规划官换成 `deepseek-v4.1-flash`。真机实测后**未改预设**，数据如下：

| 端点 × 模型 | 实测（同一时刻、同一份规划 prompt） |
|---|---|
| AMD `DeepSeek-V4-Flash`（现主位） | mini 探针 **1.8s**；完整规划 JSON **20.8s**，`finish_reason=stop` ✅ |
| AMD `DeepSeek-V4.1-Flash` | 长 prompt **0/3 成功**：#1 `429 concurrency limit (16)`、#2 **150s 0 字节超时**、#3 `429`。mini 探针 2/3 也是 429，挤进去那次 **16 token 花 48.5s** |
| 商汤 `deepseek-v4.1-flash` | **403 `model is not available in the current token plan`**（列在 /v1/models 里 ≠ 已授权） ❌ |

`DeepSeek-V4.1-Flash` 在 AMD 上是「共享并发上限 16 的排队模型」，当前长期被抢；
用它当规划官主位会把「偶发超时」变成「经常超时」，并且失败后会落到 glm-5.2 备位
（空正文）→ 整轮规划失败。**故维持 `DeepSeek-V4-Flash` 不动。**

想临时试用时的**零代码**办法：AI 流水线配置页的「角色路由覆盖」填

```json
{"planner":{"model":"DeepSeek-V4.1-Flash"}}
```

再点「按路由装配」即可；清空该框即回退预设。这正是 `roleOverrides` 当初存在的理由
——模型代际与端点可用性变动极快，不该每次都要改代码重新编译。


## 十一、规划链备用位：glm-5.2 → `deepseek-v4-flash`（实测裁决）

第八节留下的"备用位仍是 glm-5.2"这一项已处理。三 个理由都是实测：

| 判据 | 证据 |
|---|---|
| ① glm-5.2 作备用等于没有备用 | 长 prompt 下思考链吃满预算、正文恒空：规划 prompt 实测 `reasoning_tokens` **1338 / 4436**（4096 与 12000 两个预算各测一次） |
| ② `deepseek-v4-flash` 实测可用 | **同一份规划 prompt：11.4s 出完整 3 章大纲 JSON，`reasoning_tokens` 只用 435**，`finish_reason=stop` |
| ③ 它本来就是本仓库的 house 值 | 写手备选（K2）与标题官主力（K3）都用它——少一个模型就少一处要单独跟进的失效模式 |

改动（`lib/ai_pipeline/fixed_workflow_preset.dart`）：

- `sensePlanner` 由 `K1 + glm-5.2（temp 1.0）` 改为 `K1 + deepseek-v4-flash（temp 0.8）`；
  该端点是规划/审校/写手/编辑四条链共用的备用位，一次改到位。
- `endpoint()` 增加可选 `maxTokens` 形参（缺省仍 4096），`sensePlanner` 单列 **12000**。
  **这一项很关键**：备用位原先吃 4096 默认，正是它把大纲 JSON 截断在 `"origin"`
  字段中间 → 解析失败 → 整轮规划失败。只换模型不换预算等于没修。

**验证口径的诚实说明**：上面 ② 的 11.4s 是在 **K2** 上测到的同一模型同一 prompt；
K1 当时连续两次回 `429 inference exceeds tpm/rpm limit`——那是我自己在这一小时里连打
了好几发大 prompt 探针（glm 4096、glm 12000、dsf K1、dsf K2、dsf K3）把 K1 的滑动
窗口压满了，属"探针自身造成"，不是 K1 不可用（memory: `sensenova-endpoint` 已记）。
故**保持 K1 不变**（只换模型），不去动角色↔Key 的既有分配。

测试钉住：`fixed_workflow_preset_test.dart` 新增三条断言——规划链备用位首个模型必须是
`deepseek-v4-flash`、规划链任何位置都不得再出现 `glm-5.2`、备用位 `maxTokens >= 12000`。

SenseNova `kimi-k3` 反复 429，**去AI味编辑这一环在第 1/2 章基本没跑成**
（日志里是「润色失败，保留原文」），于是交出去的是写手原稿——分句、对白密度
都还是初稿形态。这与"管道通了"不矛盾：**通路已通，卡在编辑环节的端点可用性**。

## 十三、剩余 / 已知

- 离线模板引擎的**章中**衔接词（`说来也巧，` 等 18 条）仍会出现在段首——它们承接上一段是合法的，
  只在**章首第一句**才构成断层。故本轮只卡章首，没有进一步收紧。
- 离线引擎每章仍会重新随机"对手/盟友/地点"（只有主角名承接）。要彻底一致，得把角色/地点也回填进 `usedConfig`。
- 一键生成页的 `useLlm` **默认值仍是 false**，但首次启动会自动接入本机密钥；
  真正没有任何 Key 的机器仍走离线引擎 + 醒目横幅（不是静默降级）。
- **编辑环节是当前最脆的一环**：`kimi-k3`（K2）当晚反复 `429 tpm/rpm`，
  两个备用位又同时超时，于是「保留原文」——润色没跑成的章，番茄闸门的
  对白占比/句长/水段四项会亮红。端点的可用性波动一改善就能好转，但也可考虑
  在「润色失败」时给写手 prompt 补一条初稿就要满足的句式约束（待定，未实施）。
- `role_workflow_live_test.dart` 的 90s 路由超时仍未重估：AMD 今晚几乎每次都
  先耗满 90s 才切备用位，整轮因此多烧了约 20 分钟。备用位已能兜住，所以只影响
  耗时不影响成败——但重估它能让这个用例跑得快很多。
- `role_workflow_live_test.dart` 的 `gate.hasVeto` 断言目前是红的（见第十二节的
  内容质量归因）。这是**内容侧**待收敛项，不是通路问题。
