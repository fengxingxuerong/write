## 十七、2026-09-26 门禁 v7 第 16 项根因修复：关卡5 核查预算逐档重试

### 根因（第十六节线索的直接落地）

`run_fact_check` 走 `PLANNER_CHAIN`（主位思考型 `glm-5.2`，链自身 `max_tokens=8000`），但调用点把预算**硬压到 3000**。思考型模型的 reasoning 先吃预算，3000 档下极易「思考链有输出、正文为空」——`call_chain` 视为空结果切下一位，整条链跑完返回 `""`，`parse_json_from_llm` 拿不到 JSON → 返回 None → 章节记 `error`。v7 三章核查执行失败即此。与缺陷清单 #1（2026-09-12 pro 角色 max_tokens 吃空）同一模式复发，说明**预算与思考型链不匹配要靠断言守住，不能靠人记**。

### 改动

- `scripts/novel_pipeline.py`：新增 `FACT_CHECK_BUDGETS = (8000, 16000)`；`run_fact_check` 改为逐档重试，每档失败打印 `[核查] 预算 X 未取到合法 JSON（思考链吃满/解析失败），提到 Y 重试`，全档失败才返回 `None`

- `scripts/test_pipeline_reliability.py`：新增 3 项单测——① 首档空输出须提额到 16000 重试并成功；② 全档失败返回 None 且调用次数＝档数（不伪装成「0 处编造」）；③ 下限守卫 `FACT_CHECK_BUDGETS[0] >= PLANNER_CHAIN[0]['max_tokens']` 且 ≥ 8000、两档递增（防再次退回 3000）

## 十八、2026-09-26 门禁 v7 第 13 项根因修复：世界观专名清单注入写手与定点修

### 根因（都在提示词侧，不在模型能力）

把「评审 → 定点修 → 再评审」整条链路拉直后，失败是**必然**而非偶然：

1. **修复侧（决定性）**：`fanqie_review.fix_prompt(review, content)` 只把评审结论抄成一行「- 一致性：大纲世界观专名 12 个在正文一个都没出现…」，**提示词里一个专名都没有**。定点修模型收到的指令是「把世界观写进正文」却不知道本书世界观叫什么——修不动是意料之中，v7「定点修一轮后仍残留」由此解释。
2. **生成侧**：`scene_prompt` 注入的是整段 `world` JSON（「本书世界观（必须沿用）」），而评审用的是 `extract_world_terms` 切出的**专名**、按**字面命中**计数。写手自由转述设定 ⇒ 0 命中 ⇒ 直接记「世界观未落地」（重写级阻断项）。

结论：这是「检测口径（字面命中）与提示词投放（整段描述）不匹配」的配置缺陷，与 #11 同属可测可防的工程问题。

### 改动（Python 主链路 + Dart 同口径）

- `scripts/fanqie_review.py`：`world_consistency` 增 `missing` / `missing_total`（最多 8 个）；评审文案补「待补：…」（「世界观专名」「没接住设定」等字面契约不变，门禁第 13 项照旧能数）；`fix_prompt(review, content, world_terms=())` 在命中世界观专名问题时插入「【世界观专名·本条为阻断项，必须解决】」，点名缺哪几个、至少补 `min(5, 缺失数)` 个，要求**按字面照抄**（禁近义词/简称/拼音）、禁列清单、禁整段解释设定；`metrics` 增 `world`
- `scripts/generate_novel.py`：`scene_prompt(..., world_terms=())` 增「【世界观专名·本章必须落地】」，要求本场景至少带出 2 个、全章 ≥4 个（超 10 个截断并注明）；`_quality_repair_prompt` / `_quality_repair_in_chunks` 透传；Phase 1.5 质量修复轮的 `review_chapter` 一并补 world_terms（此前这条路径根本不查世界观落地，与 pipeline 口径不一致）

- Dart：`FanqieGateReport.worldMissing` + `fixPrompt` 专名区块 + 评审文案待补清单；`test/engine/quality/fanqie_gate_checker_test.dart` 增 2 项

## 十九、2026-09-26 门禁 v7 第 4 项根因修复：定点修提示词补字数下限

### 排查（先证伪「模型乱压」的猜想）

`run_smoke_gate` 第 4 项「编辑链无过度压缩告警」在 v7 记了 4 次 WARN。把日志与代码对齐后确认：

1. **4 次全部发生在 `[评审修]`（定点修），不是 `[编辑] 润色`** —— 润色那次是 4388→3950（89.9%，过线）。问题在 `fix_prompt` 这条链。
2. **建议级「压到 3000 内」没有进提示词**：`fix_prompt` 只收 `重写/修改` 级问题，`结构：本章 4087 字偏长`（建议级）被正确过滤（拿 v7 四章的评审记录逐条实测，`prompt 是否含「压到」`全为 False）。所以不是「评审让改短、代码不许短」的直接打架——**那个隐患存在（见下），但不是这次的原因**。
3. **真因：`【改写要求】` 只有压缩指令，没有任何字数下限**：
   > 「删掉所有「删了不影响剧情」的段落；句子尽量控制在 25 字内；段落不超过 3 行；对话占比提到 25%~45%」
   
   对模型来说这是一份「整章重写规格」：删水段 + 短句 + 短段 + 提高对白比，合起来必然把 3400~6000 字的章压掉 30%~75%。而**字数下限只存在于代码侧的事后守卫**（`apply_text_patch` 0.85），于是每次都是「模型照做 → 产出被整份拒 → 定点修白跑 → 原文带着问题进入下一轮」。第 1 章 90.5 分修完仍带阻断项，就是这么来的。
4. 另有隐患一并堵上：评审若真给出修改/重写级「篇幅偏长」，会与 0.85 守卫正面冲突（3000 < 3474，两条都听就不可能同时满足）。提示词里必须写明**听谁的**。

### 改动

- `scripts/fanqie_review.py`
  - 新增 `FIX_MIN_RATIO = 0.92`（比 0.85 守卫高 7 个百分点，留足改写误差余量；提示词严格、守卫兜底）
  - `fix_prompt` 在硬伤清单**之前**插入「【字数硬约束·先看这条】改写后正文不得少于 N 字（原文 M 字，最多允许压缩 8%）」，并给出冲突裁决：「若评审意见（如「篇幅偏长」）与本下限冲突，以本下限为准：压缩诉求请用「改写」（并句、去修饰、换更短的表达）满足，不靠删段」
  - 「删掉所有「删了不影响剧情」的段落」→「只删与剧情无关的水段（删多少就补多少，见上文【字数硬约束】）」
- `lib/engine/quality/fanqie_gate_checker.dart`：文件级 `const double fixMinRatio = 0.92` + `fixPrompt` 同款条款（`words > 0` 才发），同步改掉同那句「删掉所有…」
- `scripts/test_world_landing.py`：新增 4 项——下限数字与冲突裁决出现在提示词、**「提示词下限必须严于代码守卫」的反向守卫测试**（守卫若被调高于 0.92 会直接红）、措辞已改、空正文不发下限区块

### 验证（拿 v7 四章真实正文重算提示词）

| 章 | 原文字数 | 提示词下限（92%） | 0.85 守卫线 | v7 实际产出 | 结果 |
|---|---|---|---|---|---|
| 1 | 4254（修复时点日志记 4087） | 3913 | 3616 | 2847 | 被拒 |
| 2 | 3582 | 3295 | 3044 | 2718 | 被拒 |
| 3 | 4176 | 3841 | 3549 | 2707 | 被拒 |

四章下限全部高于守卫线 ⇒ 模型只要遵守字数硬约束，产出就能通过守卫，**定点修从「必被拒」变成「可落地」**；同时 0.85 守卫不放宽，继续兜底。

- `python -m unittest discover -s scripts` → **Ran 53 tests OK**（49→53）；`ruff --select=F,E9` 全绿；`compileall` 0

- 过程性教训（已进测试）：`int((1 - 0.92) * 100)` 因浮点得 **7** 而非 8，提示词会写「最多允许压缩 7%」——用 `round()`，并把「下限 vs 守卫」的相对关系写成断言，不靠人记

## 二十、2026-09-26 门禁 v7 第 16 项治理：编造命中从「只记录」变「即处置」

### 证据链（先确认问题在哪一层）

拿 v7 的 `fact_check` 记录逐条读（含 `evidence` 字段），六处命中分两类：

| 断言 | 核查依据 | 性质 |
|---|---|---|
| 老周替你看夜，看了七年 | 数字台账确立七年，但无「老周看夜七年」的归属记录 | 台账有数、归属未确立（半真） |
| 老周求我宽限三天／欠我多少 | 前文无此事实 | 新背景细节以既定事实口吻引用 |
| 我派了人看着她（灵雪）在河沟边 | 前文未确立 | 同上 |
| 命火令背面有凹槽，石板底下是锁孔 | 前文命火令仅为进渊阁凭证 | 同上（后章已复用该细节） |
| 地契在渊阁，不在屋里 | 前文未确立地契存放处 | 同上（第 3 章还在用） |

再看处置路径——**根本没有**：`run_fact_check` 命中后只 `print` + 落 `fact_check` 记录，正文一字不动，也没有任何回灌动作。也就是说：**这六处会原样进成书，门禁第 16 项必然 FAIL，再跑一百遍也不会好**。写手侧同样没有约束，后续章节会继续凭空补细节。

### 改动（修复侧回灌 + 生成侧预防）

- **`fact_fix_prompt`（新）**：只处置命中的断言，每处三选一——①删；②改写成非断言（「据说…」「他也不确定…」），确保后续章节不把它当既定事实；③确为剧情必需时在本章内补出来龙去脉（谁、何时、为何、在哪），让它成为本章首次确立的设定。其余段落一字不改，字数下限沿用 `FIX_MIN_RATIO`（**禁止以删代修**）。
- **`fact_check_stage`（新）**：`核查 → 命中即定点修 → 复检`，两条铁律：
  1. **只有复检命中数下降才采纳，否则回滚**，保留原文与首轮命中——「换了段文字」绝不等于「问题解决了」（与评审修同一验收哲学）；
  2. **台账口径始终是前章**：复检用的是修复前就存在的户籍表/数字台账/跨章状态，**绝不回灌自证**——先把编造写进台账再复检等于把检查废掉，这条绝不能开。
  - 成本：0 命中章零额外开销；命中章多 2 次调用（修复 + 复检）。
- **写手预防**：`scene_prompt` 加【事实与数字硬约束】——数字只准取自台账、台账没有的一律不许凭空写；背景细节（债务/年份/地点/师门/旧约/存放处）首次出现必须在本章交代来龙去脉，禁止以「既定事实」口吻引用。
- 两处调用点（主循环 7.60、结构补章）改走 `fact_check_stage`，`fact_check` 记录格式不变（`idx/fabrications/error` + 新增 `repaired`），门禁第 16 项读取逻辑**零改动**。

## 二十一、2026-09-26 场景规划大面积降级根因排查与门禁第 17 项加固

### 根因

在分析 `data/generated/smoke_gate_v7.smokegate.log` 时发现，4 章中有 3 章（第 1、2、4 章）打印了：
> `[规划] LLM 场景规划失败，使用默认「起承转合」骨架兜底`

排查代码 `scripts/novel_pipeline.py`（原 915-925 行与 1891-1903 行）发现：
1. **预算与思考型规划链冲突**：`PLANNER_CHAIN` 主位是思考型 `glm-5.2`，链配置 `max_tokens=8000`；但两处场景规划调用均硬编码 `max_tokens=2000`，且两次重试使用完全相同的 2000 预算。当大纲、跨章状态、人物/事实台账注入较长时，思考链输出占满 2000 token，导致正文输出截断为空，`parse_json_from_llm("")` 失败。这与缺陷清单 #1（pro 角色 max_tokens 吃空）和 #11（关卡5 编造核查 3000 token 预算不足）完全是同一机理复发。
2. **静默降级且不可观测**：
   - 规划失败后直接退回无世界观、无事实锚点的默认起承转合兜底骨架（400/400/400/400 字）；
   - 写手在兜底骨架下拿不到任何场景级世界观设定要求，只能自由脑补，直接导致后续第 1/2/3 章连挂「世界观未落地」阻断项，并在第 2 章发生 6 处无事实依据的编造；
   - 章节产物未记录规划来源，门禁验收对此完全无感知。

### 改动

1. **场景规划逐档重试与日志收敛**：
   - `scripts/novel_pipeline.py` 新增 `SCENE_PLAN_BUDGETS = (8000, 16000)`；
   - 提取公共函数 `plan_scenes_or_fallback`，支持分档重试（8000 失败提档至 16000 重试），分流打印空输出（思考链吃满/超时）与非法 JSON 原因，全档失败才降级；
   - 章节记录新增 `scene_plan: "llm" | "fallback"` 字段并随 JSONL 落盘。
2. **冒烟门禁加固第 17 项**：
   - `scripts/run_smoke_gate.py` 新增第 17 项「场景规划无静默兜底降级」；
   - 任何章节 `scene_plan == "fallback"` 直接判 FAIL，拦截因规划降级引起的隐性劣化；
   - 兼容历史产物：无 `scene_plan` 字段时降级 WARN 提示不拦截。
3. **单测覆盖**：
   - `scripts/test_pipeline_reliability.py` 新增 `ScenePlanReliabilityTest` 5 项测试：首档成功验证、首档空输出提档至 16000 验证、全档失败降级验证、门禁统计拦截验证、历史产物兼容验证。

### 验证
